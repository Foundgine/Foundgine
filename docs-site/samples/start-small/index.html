Start small

Two shop APIs, one in C# and one in Java, are the smallest Foundgine applications in the repository. Read them to see what Foundgine is, why it exists and how it plugs into the stack you already use.

What, why and how

  • What: you declare your data once: what the models mean, how they relate, where they are stored and who may see which rows. Foundgine runs every request through that declaration.
  • Why: the same rules apply on every protocol. A GraphQL call and an MCP call for an AI assistant cannot drift apart, because there is only one set of rules to maintain.
  • How: a short configuration class, a provider for the ORM you already have (EF Core or JPA), one authorization policy and a token bridge. About 285 lines of C# or 544 lines of Java, tests excluded.

Read the sources: C# Foundgine.Shop and Java foundgine-shop. Each has a conventional baseline next to it (Hot Chocolate + EF Core, Spring) so you can compare the code.

How configuration works, and why it matters

All of Foundgine’s configuration lives in one class, ShopModel. It states three things and nothing else:

  • Semantics: which models relate to which. WithMany also declares the inverse, so Customer.Orders and Order.Customer come from one line.
  • Persistence: the real table and column names (tbl_customer, cust_id). Legacy schemas keep their names; the API does not inherit them.
  • Mapping: how a model member maps to a storage member. In these samples each class is also its own storage type, so every member maps to the member of the same name.

Why it matters

  • One place to read. Meaning, storage and relationships are not spread across resolvers, controllers and ORM mappings.
  • Mistakes fail at startup. Build() validates the declaration and reports every problem at once, instead of the first request failing in production.
  • Less to write. In C#, keys are the mapped Id members and foreign keys are found by name (Order.CustomerId), so there is no key or connection configuration. In Java, the foreign keys are stated once per relationship and serve both directions.
  • Every protocol reads it. GraphQL and MCP use the same model, so adding a protocol adds no mapping code.

Configuration

ShopModel.cs (abbreviated)
public sealed class ShopModel : FoundgineModel
{
    public override void Configure(FoundgineModelBuilder model)
    {
        // Semantics: relationships. WithMany also declares Customer.Orders.
        model.Semantic<Order>(s =>
        {
            s.HasRelationship(x => x.Customer).To<Customer>().WithMany(x => x.Orders);
            s.HasRelationship(x => x.Lines).To<OrderLine>();
        });

        // Persistence: the legacy names.
        model.Persistence<Customer>(p =>
        {
            p.ToTable("tbl_customer");
            p.Property(x => x.Id).HasColumnName("cust_id");
            p.Property(x => x.Email).HasColumnName("email_addr");
        });

        // Mapping: model == storage type.
        model.Configure<IdentityEntityMap<Customer>>();
    }
}
ShopModel.java (abbreviated)
public final class ShopModel extends FoundgineModel {
    @Override public void configure(FoundgineModelRegistrar model) {
        model.configure(CustomerSemantics.class);
        model.configure(CustomerTable.class);
        model.configure(Maps.CustomerMap.class);
        model.configure(Connections.class);
    }

    // Semantics: relationships. Customer.orders also defines Order.customer.
    static final class CustomerSemantics extends FoundgineModelConfiguration<Customer> {
        @Override public void configure(FoundgineModelBuilder<Customer> m) {
            m.toEntity("Customer");
            m.hasMany("orders", Order.class).withOne("customer");
        }
    }

    // Persistence: the legacy names.
    static final class CustomerTable extends FoundginePersistenceConfiguration<Customer> {
        @Override public void configure(FoundginePersistenceBuilder<Customer> m) {
            m.toTable("tbl_customer"); m.hasKey(Customer::id);
            m.property(Customer::id).hasColumnName("cust_id");
        }
    }

    // Relationship -> foreign key, one connection for both directions.
    static final class Connections extends FoundgineConnectionConfiguration {
        @Override public void configure(FoundgineConnectionBuilder c) {
            c.hasRelationship(Customer.class, Order.class).using(Customer.class, Order.class)
                    .hasForeignKey(Order::customerId).references(Customer::id);
        }
    }
}

Ready to plug into EF Core and JPA

Foundgine does not replace your ORM and does not generate or populate your entity objects. EF Core or JPA stays the authority for schema, keys and the database. Foundgine plans the query, applies authorization, and hands the ORM a query it already knows how to run.

  • C# and EF Core: one registration line, AddFoundgineEf(metadata, (_, o) => o.UseNpgsql(cs), o => o.UseEngineProvider()). Your DbContext options stay yours.
  • Java and JPA: you create the normal EntityManagerFactory, then give Foundgine JpaOrmProvider.compiler(registry) and JpaOrmProvider.execution(registry, emf). Your @Entity classes keep their JPA annotations.
  • No second ORM: reads go through the engine, so authorization cannot be skipped by calling the ORM facade directly.

Registration

Program.cs
// Your DbContext options stay yours; Foundgine plans, authorizes and hands EF Core the query.
builder.Services.AddFoundgineEf(
    metadata,
    (_, o) => o.UseNpgsql(cs),
    o => o.UseEngineProvider());
Main.java (abbreviated)
// You create the normal JPA EntityManagerFactory; your @Entity classes keep their annotations.
var emf = Persistence.createEntityManagerFactory("foundgine-shop", props);

var orm = FoundgineOrm.<Void>configure()
        .metadata(metadata)
        .entities(GeneratedOrmMaps.entityTypes())          // generated at build time
        .generatedModels(GeneratedJpaModels.create())      // generated at build time
        .build();

JpaOrmProvider.compiler(orm.registry());
JpaOrmProvider.execution(orm.registry(), emf);

Automatic AOT generation

Discovery work is moved from request time to build time, in both languages. The generated code is plain source that you can read.

  • Java: an annotation processor runs during compilation. It finds the classes marked @FoundgineOrmEntity and generates GeneratedOrmMaps and GeneratedJpaModels, which Main passes to the JPA provider. In the sample’s pom.xml this is one annotationProcessorPaths entry and one package argument.
  • C#: a Roslyn source generator, Foundgine.Providers.Aot.Generator, emits GeneratedMetadata from [FoundgineModel] and [FoundgineConnection] attributes. The Supply Chain starter references it as an analyzer. The smallest C# sample, Foundgine.Shop, declares its model fluently and does not use the generator.

Limits, stated plainly. The generators describe your model; they do not create entities. The Java sample still needs the @FoundgineOrmEntity marker on each JPA class, and a fully annotation-free registration path is not there yet. A successful generator build is not proof that your application publishes as Native AOT: check the publish output and trimming warnings in your own deployment.

The simplest semantic setup

“Semantic” here means the model describes meaning, not tables: an Order has a Customer and Lines; a Line has a Product. Callers ask in those terms and Foundgine turns the request into a checked plan. The simplest setup is three steps:

  1. Name the relationships in the model, as above.
  2. Write one row-level rule. In the shop: a customer sees only their own Customer row and their own Orders. Managers see everything.
  3. Bridge the token. The validated JWT becomes a short-lived signed warrant; the rule reads the customer id from that claim, never from request input.

The rule

Auth.cs (abbreviated)
public AuthorizationPredicate? GetPredicate(EntityId entityId, AuthorizationOperation operation)
{
    // Only for customers, only for reads, only on Customer and Order.
    var row = AuthorizationPredicate.Member(AuthorizationPredicate.ResourceParameter("resource"), member);
    return AuthorizationPredicate.Equal(row,
        AuthorizationPredicate.Member(AuthorizationPredicate.ContextParameter("user"), "CustomerId"));
}
ShopPolicy.java (abbreviated)
@Override
public AuthorizationPredicate getPredicate(EntityId entity, AuthorizationOperation operation) {
    // Only for customers, only for reads, only on Customer and Order.
    var row = AuthorizationPredicate.member(AuthorizationPredicate.resourceParameter("resource"), member);
    return AuthorizationPredicate.equal(row,
        AuthorizationPredicate.member(AuthorizationPredicate.contextParameter("user"), "customerId"));
}

Why it matters

  • Stated once, enforced at every level. The planner applies the rule at the root and at each nested entity, so customer { orders { lines } } cannot leak another customer’s rows.
  • Fails closed. If the claim is missing, the rule matches no rows.
  • Same rule on every protocol. In C#, MCP is opt-in (Mcp:Enabled=true) and reuses the model, the rule and the JWT bridge. The Java shop sample serves GraphQL only.
  • Testable. The rule is checked by the adversarial suites described on the security page.

Run it

Both samples start with one script.

Commands

cd src/csharp/samples/Foundgine.Comparison
./run.sh                               # Postgres + Foundgine.Shop on :5001 (GraphQL and MCP)
./run.sh parity                        # run both apps, diff their GraphQL answers, smoke-test MCP
python3 tools/mint_token.py customer 1 # a token for your own requests
cd src/java/samples/foundgine-comparison
./run.sh                               # Postgres, Foundgine :5001 and the Spring baseline :5002, then a parity diff
./run.sh foundgine                     # Foundgine alone: exact row-level and denial checks against :5001

Needs Docker (PostgreSQL only). C#: .NET 10 SDK and python3. Java: JDK 21+ and Maven; the Java sample's own README says its runtime checks are not yet confirmed, so treat its output as a first run.
