Foundgine: Configurable Semantic & Execution Boundary

Foundgine separates application meaning, persistence mapping, authorization, and physical execution from the APIs, workflows, and AI agents that consume them. Configure capabilities once with language-idiomatic fluent APIs, resolve operations against application-defined semantics, and execute deterministically through SQL, EF Core, or JPA—without making an API framework, ORM, database, or AI model the center of your architecture.

Callers describe intent. The semantic model defines meaning. Authorization determines authority. Planning defines logical execution. Providers define physical execution.

Conventional Apps First

Built for standard .NET 10 and Java 27 backend services first. Foundgine requires no LLM, MCP server, GraphQL endpoint, or agent framework—those are optional consumer adapters.

Authority Stays in the Host

Discovery, candidate retrieval, aliases, model output, and caller arguments are never permission. Every request binds to a host-owned SecurityExecutionContext and cryptographic warrant.

Incremental Adoption

Keep existing EF Core DbContext, JPA EntityManager, PostgreSQL databases, Hot Chocolate, GraphQL Java, Redis, Keycloak, and Temporal infrastructure in place.

What Foundgine Is Not

Foundgine is not an ORM, a GraphQL server, an AI agent framework, an identity/authorization server, a workflow engine, a database engine, or a generic SQL builder. Its sole purpose is the governed boundary between semantic intent and controlled provider execution.

Why Foundgine: One Governed Execution Boundary Across Every Interface

Most applications implement the same business capability more than once: an API resolver applies one set of rules, a background worker applies another, an MCP tool adds its own checks, and an AI integration translates natural language into yet another execution path. Over time, validation, tenant scoping, field visibility, approval requirements, and persistence behavior drift. A secure endpoint does not make a second endpoint secure, and a prompt instruction is not an authorization policy.

Foundgine addresses that duplication by placing a semantic execution boundary between callers and data providers. The application defines what entities and operations mean, the host supplies trusted identity and policy, the runtime resolves and authorizes a request, and a provider executes the resulting constrained plan. GraphQL, MCP, application code, and workflow activities are consumers of that same boundary—not independent implementations of business authority.

Without a shared boundary

  • Rules and authorization are repeated in controllers, resolvers, jobs, and agent tools.
  • Tenant and row filters can be omitted on a new interface or nested relationship.
  • Natural-language retrieval can be mistaken for permission or treated as a confident guess.
  • Each integration develops its own mutation, approval, retry, and audit semantics.

With Foundgine

  • Semantic meaning and persistence mapping are configured independently of the caller.
  • Host-owned identity and authorization constrain the operation before provider execution.
  • Ambiguous intent is clarified or rejected; retrieval scores never grant authority.
  • Adapters converge on shared planning, provider execution, and execution evidence.

Where the main components fit

Domain application

Owns business concepts, invariants, operation definitions, and the decision to expose a capability. Foundgine does not replace domain services or application workflows.

Semantic model

Names entities, fields, aliases, dimensions, relationships, and operation capabilities independently of physical tables and columns.

Runtime & planner

Resolves structured intent, applies bounded grounding, obtains authorization, creates a logical plan, and lowers it into provider-facing execution IR.

Identity & policy

The host validates authentication and supplies trusted subject, tenant, claims, and policy decisions. Foundgine binds the authorized scope to execution.

Providers

Translate the provider-independent plan into supported SQL or ORM operations and enforce the provider contract. Physical execution remains separate from semantic meaning.

Workflow integrations

Temporal can coordinate durable steps, timers, retries, approvals, and compensation. Each activity obtains fresh authority and invokes Foundgine for the underlying operation.

Execution lifecycle: intent to evidence

The exact stages and their contracts are detailed in the canonical lifecycle reference. At a product level, a request moves through these boundaries in order; later stages cannot retroactively turn an untrusted input into authority.

  1. Intent: a caller supplies a typed request or structured intent document.
  2. Semantic resolution: the runtime maps names and relationships to the configured model; bounded retrieval may propose candidates, but ambiguity is surfaced.
  3. Authorization: the host-owned security context and policy determine allowed operations, rows, and fields. A warrant binds that authority to the request.
  4. Execution planning: the planner creates a provider-independent logical plan and lowers it to ExecutionIR with the required constraints.
  5. Provider conformance: the selected provider validates and translates supported IR nodes into its physical query or mutation mechanism.
  6. Execution & evidence: the provider executes within the host's transaction and operational controls; the runtime returns a result and applicable execution evidence.

Security is part of the execution contract

  • Host-owned identity: authentication and claim validation belong to the host or trusted identity integration; caller-provided subject and tenant values are not authority.
  • Tenant and row isolation: authorization contributes constrained predicates that must survive planning and provider lowering.
  • Field policies: permitted projections and field-level restrictions are applied before data is returned; masking/redaction is distinct from authorization to read.
  • Authorization warrants: signed, scoped execution authority binds the operation to its security context and relevant plan provenance.
  • Replay and idempotency controls: single-use/replay defenses and mutation idempotency protect the applicable execution paths; deployments must configure the shared backing stores required for distributed guarantees.
  • Audit: execution evidence and durable audit integrations support traceability; they do not replace operational retention, monitoring, or incident-response controls.

Read the security and warrant specification, mutation lifecycle, and audit and observability design for the detailed contracts and deployment requirements.

Retrieval, mutations, approvals, and receipts

Retrieval is a bounded semantic-discovery aid, not an authority system. The runtime grounds candidates against configured entities, fields, aliases, relationships, and limits. If candidates remain ambiguous, the request requires clarification or is rejected rather than silently selecting a convenient interpretation.

Mutations follow a controlled lifecycle: propose a mutation, validate and dry-run the proposed plan, obtain the required approval against the exact proposal, then execute under fresh valid authority. The resulting execution receipt records the outcome and relevant provenance. Approval is not a substitute for rechecking authorization at execution time.

GraphQL, MCP, and Temporal are integrations—not the semantic core

GraphQL

GraphQL adapters translate schema selections and mutation requests into Foundgine operations. Hot Chocolate remains the GraphQL server; Foundgine supplies the shared semantic and authorization boundary.

MCP & agents

MCP exposes bounded tools for capability discovery and governed execution. Agent frameworks may choose tools and formulate intent, but neither prompts nor model output can mint authority.

Temporal

Temporal owns durable orchestration. Foundgine owns authorization and execution of each business operation; workers should obtain fresh activity-scoped authority on every attempt.

See GraphQL, identity, and Temporal integrations, MCP and agent integration, and the agent clarification and execution walkthrough.

Deployment shape

A typical deployment runs a Foundgine-enabled application service beside its database and optional shared infrastructure. The host validates incoming credentials, builds the trusted security context, registers the semantic model and provider, and exposes only the interfaces required by the application. MCP and GraphQL can be hosted by the same service or separate adapters; Temporal workers are commonly deployed separately from the HTTP API. Redis-backed replay/session controls, durable audit, event stores, and outbox dispatchers are optional infrastructure selected according to the guarantees the deployment requires.

Canonical 12-Stage Lifecycle & Component Topology

Every entry surface—typed C#/Java code, dynamic queries, JSON intent, Hot Chocolate GraphQL, GraphQL Java, MCP tools, Microsoft Agent Framework, LangChain4j, Spring Boot, or Temporal activities—converges on one monotonic pipeline before any provider work occurs.

1. SemanticOperationGraph

The canonical security object for reads (and SemanticMutationOperationGraph for writes). Logical traversals (e.g., Customer.transactions) are expanded into intermediate entities and edges before authorization runs so shortcuts cannot tunnel past denied entities.

2. Plan Binding Provenance

SemanticPlan carries an immutable SemanticPlanAuthorizationBinding recording the exact frozen semantic contract fingerprint and authorization decision fingerprint. Planner rewrites must preserve the binding; tampering or drift fails closed.

3. ExecutionIR & Security Proof

ExecutionIRCompiler refuses unbound plans. The final execution gate requires a provider security proof bound to the exact provider plan and exact ExecutionIR, then emits immutable ExecutionEvidence and ExecutionReceipt records.

Stage-by-Stage Execution Contract, Inputs, Outputs & Fail-Closed Invariants

Each stage in Foundgine's monotonic pipeline consumes an immutable artifact from the preceding stage and produces a cryptographically verifiable artifact for the next stage. No provider or adapter can jump ahead or mutate an upstream artifact without invalidating downstream fingerprints.

Model Validation Rules, Filter Operators & Pagination Semantics

Single-Pass Model Validation

Calling new MyModel().Build() (.NET) or new MyModel().build() (Java) runs deterministic graph checks before returning a frozen MetadataRegistry:

  • Every mapped entity must declare a valid primary key (HasKey) and resolve all mapped columns.
  • Every relationship foreign key must match source/target CLR or Java field types exactly.
  • Logical traversals must resolve every intermediate hop across registered relationships without cycles or dangling targets.
  • Produces a deterministic SHA-256 Contract Fingerprint embedded in every downstream plan and warrant check.

Supported Filter & Quantifier Operators

All filter trees lower identically across ADO.NET SQL, EF Core, JPA Criteria, and InMemory providers:

  • Comparison: Eq, Neq, Gt, Gte, Lt, Lte
  • Set & Range: In, NotIn, Between, IsNull, IsNotNull
  • String: Contains, StartsWith, EndsWith (escaped LIKE)
  • Logical: And, Or, Not (bounded by MaxFilterDepth=32)
  • Relational: WhereRelated(Some | Every | None, subFilter)

Deterministic Keyset & Offset Pagination

To prevent skipped or duplicated rows during cursor pagination across distributed replicas:

  • ExecutionIRCompiler automatically appends the entity primary key as a final deterministic tie-breaker sort column if not already present.
  • Opaque cursors encode sort boundary values bound to the plan fingerprint and are capped at MaxCursorLength = 4,096 bytes.

Lexical Grounding, Weighted Aliases & Retrieval Boundaries

Free-form language is resolved through SemanticLexicalResolver.Ground(...) (.NET) and SemanticLexicalResolver.ground(...) (Java). Approximate retrieval providers (ElasticsearchSemanticLexicalCandidateSource or PgVectorSemanticLexicalCandidateSource) only propose vocabulary candidates; the semantic graph validates structural legality and groups paths by semantic signature.

5-Phase Bounded Lexical Grounding Algorithm

When SemanticLexicalResolver.Ground(...) receives a natural-language phrase, it executes five deterministic, bounded phases before emitting a GroundingDecision:

  1. Tokenization & Normalization: Splits input into normalized lexical tokens while enforcing MaxTokens = 32 and cooperative cancellation.
  2. Non-Authoritative Vocabulary Retrieval: Queries registered ISemanticLexicalCandidateSource providers (Elasticsearch BM25 or PostgreSQL pgvector) within RetrievalTimeout = 2s for matching entity names, field names, and weighted aliases.
  3. Constrained Graph Path Exploration: Traverses legal relationships in the frozen MetadataRegistry connecting candidate entities and predicates, halting immediately if explored paths exceed MaxPathsExplored = 5,000 or Timeout = 250ms (GroundingOutcome.BudgetExceeded).
  4. Semantic Signature Canonicalization: Reduces each candidate path into a canonical structural signature (root entity + normalized filter AST + relationship hops). Multiple surface phrasings (e.g., "client" and "customer") that collapse to the same semantic signature reinforce one another rather than causing false ambiguity.
  5. Contention & Weight Threshold Gate: If ≥2 distinct semantic signatures remain viable, or the winning signature's evidence weight falls below minimumAliasWeight, the resolver fails closed with GroundingOutcome.RequiresClarification and populates CompetingInterpretations.
GroundingOutcome When It Occurs Committed Execution Behavior
Committed Exactly one semantic meaning dominates, or multiple candidates collapse onto the same signature and satisfy minimumAliasWeight. Populated Proceeds to authorization, plan binding, and execution.
RequiresClarification Two or more distinct semantic meanings remain in contention (e.g., "active customers" → AccountEnabled vs. HasRecentOrder), or alias evidence falls below threshold. null Refuses to guess; exposes CompetingInterpretations for sanitized clarification.
Unresolved No legal semantic path exists or a token has no declared vocabulary (e.g., unmodeled threshold "big" or relative date "last summer"). null Fails closed; names the exact unresolved token in Reason.
BudgetExceeded Any bounded search control fires (MaxTokens=32, MaxPathsExplored=5000, Timeout=250ms, RetrievalTimeout=2s, or Cancelled). null Fails closed with BudgetLimit; partial cutoff candidates are diagnostic-only.

Zero-Trust Security, Cryptographic Warrants & Resource Limits

Foundgine enforces defense-in-depth across every transport, planner, cache, and storage provider:

1. Host-Owned Identity & Delegation Chains

Identity, tenant, audience, and roles come exclusively from the host's ISecurityExecutionContextProvider. Delegated warrants require an explicit trusted root issuer, a complete root-to-leaf chain on SecurityExecutionContext, and a configured ISecurityWarrantDelegationTrustResolver verifying every signature and ensuring child authority never exceeds parent authority.

2. Row-Level Predicates & Fail-Closed Projection

Conditional access policies emit provider-independent predicates (e.g., resource.TenantId == context.TenantId) that travel inside the logical plan and are lowered into parameterized SQL WHERE clauses or ORM filters. An empty authorized field set fails closed rather than widening to SELECT *.

3. Plan-Cache Isolation

Provider plan caching reuses compiled physical shapes keyed by the full plan fingerprint—including authorization predicates—while binding context parameters at execution time. Cache hits never skip semantic resolution or authorization revalidation.

4. Distributed Redis Revocation & Atomic Approvals

Horizontally scaled hosts use RedisSecurityWarrantReplayStore and RedisSecurityWarrantRevocationStore (Redis/Valkey/Garnet) wrapped in AnchoredSecurityWarrantRevocationStore backed by PostgreSQL GREATEST epoch anchors. If Redis lags behind the durable anchor or is unreachable, warrant authorization fails closed.

Cryptographic Warrant Anatomy, Delegation Chains & Replay Defense

Warrant Claims & Binding

Host-minted warrants cryptographically bind execution authority to a specific runtime context:

  • iss / aud: Trusted issuer & service audience
  • sub / tid: Authenticated principal & tenant ID
  • jti / exp / nbf: Single-use nonce & tight TTL
  • rev_seq: Monotonic revocation epoch floor
  • scope / entities: Narrowed capability allowlist
  • contract_fp: Frozen MetadataRegistry SHA-256

Delegation Trust Chain Rules

When an orchestrator or agent delegates authority to a sub-agent (SecurityExecutionContext.DelegationChain):

  • Every link from root host issuer to leaf executor must verify against ISecurityWarrantDelegationTrustResolver.
  • Monotonic Attenuation: A child warrant can only narrow entities, fields, operations, or TTL—any attempt to widen tenant, role, or write scope fails closed.
  • Revoking any ancestor warrant invalidates the entire downstream delegation chain immediately.

Fail-Closed Failure Matrix

Exact runtime behavior when infrastructure or tokens degrade:

  • Expired / bad signature → SecurityAuthorizationException
  • Replayed jti nonce → WarrantReplayDetectedException
  • Redis behind PG anchor → Fail-closed (deny dispatch)
  • Empty authorized fields → Forbidden (never SELECT *)
  • Unbound SemanticPlan → InvalidExecutionPlanException

using Foundgine.Core.Security;
using Foundgine.Runtime.Authorization;

public sealed class SupplyChainAuthorizationPolicy : ISemanticAuthorizationPolicy
{
    public ValueTask<SemanticAuthorizationDecision> AuthorizeAsync(
        SemanticAuthorizationRequest request,
        CancellationToken ct)
    {
        var ctx = request.SecurityContext;
        if (!ctx.IsAuthenticated)
            return ValueTask.FromResult(SemanticAuthorizationDecision.Deny("Unauthenticated caller."));

        // 1. Enforce mandatory tenant row-level predicate lowered into SQL WHERE / EF IQueryable
        var tenantPredicate = SemanticFilter.Eq("TenantId", ctx.TenantId);

        // 2. Restrict sensitive fields unless caller holds 'finance' role
        var allowedFields = request.RequestedFields
            .Where(f => f != "UnitCost" || ctx.Roles.Contains("finance"))
            .ToArray();

        if (allowedFields.Length == 0)
            return ValueTask.FromResult(SemanticAuthorizationDecision.Deny("No authorized fields remain."));

        return ValueTask.FromResult(
            SemanticAuthorizationDecision.Allow(allowedFields, tenantPredicate));
    }
}

Deployment Topologies, Ecosystem Comparison & Wire Schemas

Foundgine scales incrementally from a single in-process application library with zero external infrastructure up to a horizontally scaled, multi-protocol enterprise execution hub.

Three Production Deployment Topologies

Tier 1 · Embedded Domain Core

Stack: Foundgine.Core + Runtime + EF Core / JPA + PostgreSQL (or SQLite).

  • Zero AI, MCP, GraphQL, or Redis dependencies required.
  • Replaces scattered repository/service authorization checks with centralized FoundgineModel + row-level predicates.
  • Compile-time AOT generators eliminate startup reflection overhead.

Tier 2 · Multi-Surface API & Agent Gateway

Stack: Tier 1 + Hot Chocolate / GraphQL Java + MCP Streamable HTTP + Keycloak + Redis.

  • Exposes identical domain rules across GraphQL (/graphql), MCP (/mcp), and MAF / LangChain4j agent loops.
  • AnchoredSecurityWarrantRevocationStore (Redis + PostgreSQL GREATEST epoch) guarantees cluster-wide single-use replay protection and instant revocation.

Tier 3 · Durable Saga & Regulated Enterprise Hub

Stack: Tier 2 + PostgresEventStore + PostgresOutbox + Temporal + BufferedDurableAuditLog.

  • Transactional outbox triggers Temporal workflows atomically with business writes; activities re-mint short-lived host warrants per step.
  • Human-in-the-loop mutation approvals (fgmcp1) and AES-256-GCM encrypted gateway envelopes produce immutable audit receipts.

Event Sourcing, Transactional Outbox, Gateway & Observability

Beyond synchronous read and mutation execution, Foundgine provides durable event persistence, transactional outbox dispatch, encrypted approval gateways, and native OpenTelemetry instrumentation—all governed by the same frozen semantic contract and host-owned security boundary.

1. Event Store & Optimistic Concurrency (PostgresEventStore)

Appends immutable domain and governance EventEnvelope records into PostgreSQL streams with strict per-stream sequence numbers and optimistic concurrency checks (ExpectedVersion). Supports stream replay, causal correlation IDs (CorrelationId / CausationId), and principal provenance metadata.

2. Transactional Outbox (PostgresOutbox)

Writes outbound integration messages into the outbox table inside the exact same database transaction as the business entity mutation. Background workers claim batches via FOR UPDATE SKIP LOCKED, enforce idempotency keys, apply exponential retry backoff, and quarantine poison messages to a dead-letter partition.

3. Encrypted Gateway Approvals (FoundgineGateway)

Provides a transport-neutral facade for high-assurance workflows where mutation proposals are persisted in PostgresFoundgineGatewayApprovalStore using AES-256-GCM authenticated encryption (key-versioned with AAD bound to tenant and plan fingerprint) until an authorized human or policy engine approves dispatch.

4. OpenTelemetry & Lossless Audit (BufferedDurableAuditLog)

Emits distributed traces (ActivitySource("Foundgine") / OpenTelemetry Java SDK) and histograms across every pipeline stage without leaking sensitive row values or raw tokens. BufferedDurableAuditLog batches signed ExecutionReceipt records with bounded backpressure so audit evidence is never silently dropped.

Performance Tuning, Caching Architecture & Capacity Planning

Foundgine separates cold-path semantic compilation from hot-path parameterized execution so production workloads amortize model validation, graph expansion, and SQL/ORM query generation across thousands of requests per second.

1. Singleton Frozen MetadataRegistry

Build MetadataRegistry once at application startup (or via compile-time AOT source generators). Never call new MyModel().Build() per HTTP request—freezing computes the contract SHA-256 fingerprint once and shares immutable lookup tables lock-free across all threads.

2. Fingerprint-Keyed Plan Cache

SqlExecutionProvider and ORM providers cache compiled query templates under SHA256(ContractFP + PlanBindingFP + Dialect). Subsequent requests with the same structural shape and authorization policy bind new parameter values (@p_auth_tenant, @p_filter_0) directly without re-running SQL compilation.

3. Redis Pipelining & Local JWKS Cache

Configure connection multiplexing (StackExchange.Redis / Lettuce) with sub-second timeouts for warrant replay/revocation checks, and cache Keycloak JWKS signing keys in memory with background refresh so token verification adds <0.1 ms per call.

4. Native AOT & GraalVM Readiness

Using Foundgine.Providers.Aot.Generator (.NET 10) or foundgine-aot-generator (Java 27) eliminates runtime expression reflection and assembly scanning, enabling sub-20 ms container cold starts and minimal RSS memory footprints.

Running Foundgine in regulated, high-availability production clusters requires deterministic readiness probes, connection pool budgeting, and ordered shutdown hooks so in-flight mutations and buffered audit receipts drain without data loss:

2. Graceful Shutdown Ordering

  1. Stop accepting new HTTP / GraphQL / MCP requests (drain load balancer).
  2. Await in-flight SemanticMutationEngine transactions up to ShutdownDrainTimeout.
  3. Flush BufferedDurableAuditLog ring buffer to PostgreSQL so every committed receipt is persisted.
  4. Close Redis multiplexers and ADO.NET / HikariCP connection pools.

using Foundgine.Core.Grounding;
using Npgsql;

// Retrieval proposes weighted lexical candidates only — NEVER bypasses SemanticLexicalResolver or Policy!
public sealed class PostgresFuzzyCandidateSource(NpgsqlDataSource dataSource) : ISemanticLexicalCandidateSource
{
    public async ValueTask<IReadOnlyList<LexicalCandidate>> FindCandidatesAsync(
        LexicalCandidateRequest request,
        CancellationToken ct)
    {
        await using var conn = await dataSource.OpenConnectionAsync(ct);
        await using var cmd = new NpgsqlCommand("""
            SELECT canonical_entity, canonical_field, alias_term,
                   ROUND(similarity(alias_term, @q) * 100)::int AS score
            FROM semantic_vocabulary_index
            WHERE similarity(alias_term, @q) >= 0.35
            ORDER BY score DESC
            LIMIT @limit
            """, conn);
        cmd.Parameters.AddWithValue("q", request.NormalizedToken);
        cmd.Parameters.AddWithValue("limit", request.MaxCandidates);

        var results = new List<LexicalCandidate>();
        await using var reader = await cmd.ExecuteReaderAsync(ct);
        while (await reader.ReadAsync(ct))
        {
            results.Add(new LexicalCandidate(
                Entity: reader.GetString(0),
                Field: reader.IsDBNull(1) ? null : reader.GetString(1),
                MatchedTerm: reader.GetString(2),
                EvidenceWeight: reader.GetInt32(3)));
        }
        return results;
    }
}

Semantic Query Optimizer Passes, Algebra & Cost Bounds

Before ExecutionIRCompiler lowers a SemanticPlan into physical SQL or ORM expression trees, SemanticPlanner executes a deterministic sequence of invariant-preserving rewrite passes. Every rewrite pass must preserve the exact SemanticPlanAuthorizationBinding fingerprint and never widen field projections or drop row-level predicates:

Optimizer Pass Transformation Performed Safety Invariant
1. Projection Pruning Removes unreferenced columns from intermediate join nodes while retaining foreign-key join columns and the root primary key. Never adds columns outside AuthorizationDecision.AllowedFields.
2. Predicate Pushdown Pushes user filters and policy-injected row-level predicates (TenantId, ownership predicates) as close to base ScanNode leaves as relational semantics allow. Never reorders across outer-join null-producing boundaries in a way that alters row visibility.
3. Redundant Join Elimination Collapses duplicate relationship traversals referencing the same parent/child edge within a single query graph into one JoinNode. Preserves cardinalities (OneToOne, ManyToOne, OneToMany) and child row predicates.
4. Deterministic Tie-Breaker Injection Appends the entity primary key (ASC) to SortNode whenever user sort keys are non-unique or omitted. Guarantees stable keyset cursor pagination across concurrent inserts/updates.
5. Cardinality & Depth Guard Verifies total expanded join fan-out, selection depth (≤32), and node count (≤256) against SecurityResourceLimits. Halts with ResourceLimitExceededException before hitting the database.

Complex business mutations rarely touch a single row. SemanticMutationGraph models multi-entity writes as a directed acyclic graph (DAG) of dependent operations—such as inserting a parent PurchaseOrder, capturing its generated primary key, inserting child PurchaseOrderLine rows, updating inventory reservations, and appending a transactional outbox event inside one atomic database transaction:

Topological Execution & Key Propagation

  • Dependency Resolution: Sorts mutation nodes topologically so parent inserts execute before dependent foreign-key child inserts, and child deletes execute before parent deletes.
  • Output-to-Input Binding: Binds generated primary keys (UUID / BIGINT) from parent mutation nodes into child foreign-key slots without exposing intermediate SQL to the caller.

  • Per-Node Policy Check: Every target entity and mutated field in the graph is authorized independently by ISemanticAuthorizationPolicy, with row-level predicates injected into UPDATE/DELETE WHERE clauses.
  • Optimistic Concurrency: Supports expected version / concurrency token assertions so stale writes abort cleanly and roll back the entire transaction.

Batch & Bulk Mutation Pipelines, Chunked Transactions & Failure Policies

High-throughput ingestion jobs, catalog imports, and scheduled reconciliations often submit hundreds or thousands of mutations rather than a single row write. Foundgine governs bulk operations through explicit chunk sizing, per-chunk dry-run authorization, and configurable atomicity policies:

1. Chunked Transaction vs. Atomic Batch Modes

  • All-or-Nothing Batch (AtomicityMode.StrictAllOrNothing): Executes all items in the mutation graph inside a single database transaction; if any item fails policy, invariant validation, or optimistic concurrency, the entire batch rolls back.
  • Bounded Chunked Batch (ChunkSize = N): Splits large mutation sets into fixed-size transactional chunks (e.g., 250 items per commit) so lock durations stay bounded and partial progress is recorded with per-chunk ExecutionReceipt IDs.

2. Deterministic Retry & Dead-Letter Handling

  • Transient deadlocks or serialization failures retry within the active chunk budget, while deterministic policy or validation rejections fail immediately without wasting retries.
  • Rejected items in partial-tolerant batch workflows emit structured rejection receipts rather than silently disappearing.

Frequently Asked Architectural Questions

Does Foundgine replace Hot Chocolate, GraphQL Java, EF Core, or JPA?

No. Foundgine complements them. Hot Chocolate and GraphQL Java act as thin transport adapters while Foundgine centralizes semantic modeling, lexical grounding, warrant verification, and row-level authorization—executing through SQL or your existing EF Core / JPA persistence layer.

Does Foundgine require AI, LLMs, or an MCP server?

No. Foundgine is designed for conventional .NET 10 and Java 27 backend systems first. AI agents, MCP, GraphQL, and Temporal workflows are optional consumer adapters over the same configured semantic capabilities.

How does Foundgine prevent LLM prompt injection from escalating privileges?

Caller input, capability discovery, retrieval scores, and model output are never treated as authority. Identity and tenant claims come strictly from host-verified tokens/warrants, ambiguous phrases fail closed with RequiresClarification, and write execution requires a host-signed fgmcp1 approval bound to the exact plan fingerprint.

How is cross-language parity between .NET 10 and Java 27 guaranteed?

Both runtimes share the five-concern fluent model, identical structural SecurityResourceLimits, and shared JSON conformance suites (src/conformance/) validated in CI on every change.
